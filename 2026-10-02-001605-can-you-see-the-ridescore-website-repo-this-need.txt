● Since PR #3, the site has been reorganized so that someone can work on the
  pages without running everything locally. Survey responses are now stored
  separately from the map data, and the changes have been deployed to
  production. Fifteen of PRs #3–#18 are merged; #13 is still open.

  Who did what: fkloosterman wrote #3–#12 as one stacked series, merged on Sept
  26. billxie22901 did #14–#18 on Oct 1, which pushed everything to production
  and fixed the deploy pipeline. #13 (bnwah) is a one-line test of the front-end
  guide.

  Key changes

  1. The pages can be edited without the database or servers (#3). Running npm 
     install, then npm run dev, serves the pages at localhost:5173 and reloads
     on save. Map tiles and the feedback service come from the shared server at
     dev.ridescoredc.com. This needs Node 20 or newer. There's still no build
     step: the files Vite serves are the files the live site serves.
  2. The pages moved out of the API folder (#7).
     - api/static/ became frontend/, and the survey's address changed from
       /feedback_mvp.html to /survey/.
     - Code that was copied into both pages (map setup, aerial imagery, crash
       layers, panel buttons) now lives in frontend/src/shared/.
     - nginx now serves the pages directly. The Python API only records survey
       responses and reports /health.
     - Any server needs a new nginx config, based on nginx/server.conf.example.
       Otherwise every page returns a 404.
  3. The database is split into three schemas (#5, #6):
     - data holds the pipeline output, which is reloaded wholesale.
     - app holds survey responses, which can't be regenerated, so they're kept
       away from reloads.
     - serving holds what the map is allowed to show.

     Table changes are applied as versioned yoyo migrations, which record what
     has already run. The old hand-run SQL file moved to api/migrations-legacy/.
  4. Survey responses are stored more reliably (#5, #6):
     - Responses now point to a street by the pipeline's own segment_id. Before,
       they used a database row number, which could point to a different street
       after a reload.
     - Each response records which published data version it was made against,
       for example ridescoredc-data-preview@0.1.
     - Before #6, no survey from the live site was ever saved, because the
       submit address was hard-coded to http://localhost:8000. It's now a
       relative path.
  5. The survey page no longer shows scores (#6, #12). Respondents used to see
     the project's rating of a street before giving their own. Roads are now
     drawn in one grey, and the weight sliders and score rows are gone. A Martin
     config example makes sure the survey's data source is the only one the
     tile server publishes. The main map at / keeps its scores.
  6. Crash map fixes (#6, #7):
     - The field names didn't match the pipeline's, so three popup rows were
       always blank.
     - For the same reason, the heatmap gave every crash the same weight.
     - The severity scale went up to 20, but the worst crash in the data is a 5.
       The scale now tops out at 5, with a baseline weight so every crash still
       shows.
  7. New setup commands (#8, #11):
     - npm run data loads the published road data.
     - npm run migrate creates or updates the survey tables.
     - npm run setup does both.
     - npm run check-env checks your settings files. It now works on Windows,
       where it used to silently do nothing, and it flags a setting written
       twice with different values.

     These scripts run through uv, which servers now need to have installed.
     Where the published data comes from can be overridden in .env. DB_PORT and
     DB_DATA_DIR are now settable, so the stack can run next to an existing
     Postgres.
  8. Deploy and CI changes (#4, #10, #12, #15–#18):
     - Lint uses the pinned ruff 0.6.9. It had been failing on develop since Aug
       1 because CI installed the latest ruff.
     - Deploys now apply migrations before restarting.
     - CI tests the migrations on an empty database (the job was renamed
       check-migrations).
     - Two merges can't deploy at the same time.
     - The production deploy now logs in as fastapi instead of ubuntu, and runs
       ssh-keyscan first so the SSH connection doesn't fail on an unknown host.
     - Fixes for problems that only showed up on a real server: uvx not being
       found during deploy, and misleading messages about the tile server.
  9. Contributor guides (#9): docs/local-frontend-development.md for page-only
     work, and docs/local-fullstack-development.md for the full stack with
     Docker and uv.

  Still open

  - Questions about how the survey tables model feedback haven't been decided.
    They include streets repeated on an out-and-back route, direction of travel,
    and identifying respondents. The PRs say these are written up separately
    for the team.
  - A deploy doesn't install Python dependencies, because the API runs on the
    system Python, so a new dependency needs root on the server.
  - Moving the shared scripts to JS modules is marked as a good hackathon task.

● Yes, there are two routes, Vite and Docker. Either way you edit the same plain
  HTML and JavaScript files in frontend/, and the site has no build step. The
  two routes differ only in what serves those files to your browser and where
  the map data comes from.

  Editing the HTML files directly

  Every change to a page is a direct edit of a static file:

  frontend/
    index.html          the map      →  /
    survey/index.html   the survey   →  /survey/
    src/shared/         config.js, basemap.js, crashes.js  (used by both pages)

  Nothing compiles or bundles these files. The file you save is the file
  production serves; on a server, nginx reads it straight from disk. Each page
  is one large HTML file with its styles and scripts inline, so it's quickest to
  search for an element ID or a piece of text than to read top to bottom.

  Route 1: Vite (npm run dev), for page work

  browser → localhost:5173 (Vite)
              ├─ pages        ← your frontend/ folder
              └─ /tiles, /api ← forwarded to VITE_UPSTREAM (default: 
  dev.ridescoredc.com)

  - What Vite is: a small development server for web pages. Here it does two
    things. It serves the pages from your folder and reloads the browser the
    moment you save. Any request for map tiles or the survey API it passes on to
    the shared dev server.
  - What you need: Node 20 or newer, and an editor. No Docker, no database, no
    Python.
  - Setup: npm install, then cp .env.example .env, then npm run dev, and open
    http://localhost:5173.
  - What you see: real map data from the dev server, and survey submissions go
    to the dev server too.
  - When to use it: layout, styling, popups, wording, and survey flow. Most
    contributors only need this route. The guide is
    docs/local-frontend-development.md.

  Vite is only a local tool. It never runs on a server.

  Route 2: Docker (npm run stack), for the full system

  browser → localhost:8000 (nginx, in Docker)
              ├─ /, /survey/  ← frontend/ folder, read from disk
              ├─ /tiles/...   → Martin  → PostgreSQL (serving schema)
              └─ /api/...     → FastAPI → PostgreSQL (app schema)

  - What it runs: four containers that copy the production setup. They are nginx
    (routes requests), Martin (turns database rows into map tiles), FastAPI
    (records survey responses), and PostgreSQL with PostGIS (the database).
  - What you need: Docker Desktop and uv, which runs the Python helper scripts,
    on top of Node.
  - Setup: copy api/.env.example to api/.env, then npm run stack. In a second
    terminal, run npm run setup to download and load the DC road data and create
    the survey tables.
  - What you see: a fully offline site on http://localhost:8000, with your own
    database and your own survey responses.
  - When to use it: changing what the survey stores, the API, migrations, tile
    server or nginx config, or testing new pipeline output from
    ridescoredc-models. The guide is docs/local-fullstack-development.md.

  Page edits work here too, but you have to refresh the browser yourself,
  because nginx doesn't auto-reload. Edits to api/main.py restart the API
  container automatically. Changes to nginx/default.conf or martin.yaml need npm
  run restart -- nginx (or -- martin).

  Using both routes at once

  Run the Docker stack, then set VITE_UPSTREAM=http://localhost:8000 in .env and
  run npm run dev. You get auto-reloading pages at :5173, with data from your
  own stack instead of the shared server. When you change that setting, edit the
  existing line rather than adding a second one; a duplicate line with a
  different value makes the tools refuse to start.

  What npm does

  npm has two small jobs here, and neither involves building the site:

  1. Installs Vite. npm install reads package.json, and Vite is its only
     dependency. It goes into node_modules/.
  2. Gives short names to commands. The scripts section of package.json maps
     each name to a command:

  ┌──────────────────────────────┬──────────────────────────────────────────┐
  │           you type           │            what actually runs            │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ npm run dev                  │ vite                                     │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ npm run stack                │ settings check, then docker compose up   │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ npm run stack:down /         │ docker compose down / logs -f / restart  │
  │ stack:logs / restart         │                                          │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ npm run data                 │ uv run scripts/load_data.py (Python)     │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ npm run migrate              │ uv run scripts/migrate.py (Python)       │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ npm run setup                │ data, then migrate                       │
  ├──────────────────────────────┼──────────────────────────────────────────┤
  │ npm run check-env            │ checks that .env and api/.env hold the   │
  │                              │ right settings                           │
  └──────────────────────────────┴──────────────────────────────────────────┘

  For example, npm run stack is just Docker, and npm run data is just Python.
  npm is used as a single set of commands so contributors don't have to remember
  the Docker and uv details.

  The two settings files

  ┌──────────┬────────────────────────────────────────────┬─────────────────┐
  │   file   │                    for                     │     read by     │
  ├──────────┼────────────────────────────────────────────┼─────────────────┤
  │          │ your laptop only: which upstream Vite      │ Vite and docker │
  │ .env     │ uses, the database port, where database    │  compose        │
  │          │ files are stored                           │                 │
  ├──────────┼────────────────────────────────────────────┼─────────────────┤
  │          │ the running app: database address and      │                 │
  │ api/.env │ password (a matching file also exists on   │ the containers  │
  │          │ the servers)                               │                 │
  └──────────┴────────────────────────────────────────────┴─────────────────┘

  To decide which file a setting belongs in, ask whether the running website
  needs it or only your laptop does. npm run check-env tells you if a setting is
  in the wrong file.

  My suggestion: start with the Vite route. It takes about five minutes and
  covers anything you'd do to the pages. Switch to Docker only when you need to
  change the database, the API or the tile server, or need to work offline.

  ## How a pointer move becomes a selected segment
  - **Pointer move (979-992):** each move adds a point to `paintPoints` and
  updates momentum. Momentum (1214-1229) compares the newest point with the one
  10 raw events back, needs at least 12 px of movement, and smooths with EMA
  0.25 on every pointer event. A 50 ms throttle then calls `enqueuePaintSnap`.
  - **Scoring (`findBestCandidate`, 1260-1346):** it runs
  `queryRenderedFeatures` on an 80×80 px box (`SNAP_RADIUS` 40) over layer
  `road-score`, and scores every sub-edge within 40 px:
    - score = `dist × penalty × contMult × revisit`
    - penalty runs from 1 (aligned with momentum) to 3.5 (perpendicular)
    - `contMult` is 0.58 if either vertex of the sub-edge is within 16 px of
  `lastCommittedEdge`
    - `revisit` is 1.14 if the segment is already selected
    - If the winner is already selected, it returns null. It never falls back to
  the second-best candidate.
  - **Adding (1438-1462, 1376-1393, 1348-1364):** the winner is pushed to
  `snapQueue` and drawn as "pending" (opacity 0.48). Once 8 items are queued,
  the oldest is checked against the stroke direction over the next 4-12 points.
  It is committed if |dot| ≥ 0.38 and otherwise dropped. Commit writes
  `selectedSegments`, `selectionHistory`, `strokeOrderedSegmentIds` and
  feature-state.
  - **On pointer up:** the remaining queue is flushed with a looser 0.22
  threshold (1464), then `pruneSelectionsFarFromRawPolyline` drops segments
  added this stroke that sit more than 62 px from the stroke (1546-1555). A
  short gesture (under 14 px and at most 10 events) counts as a tap (999-1013).
  - **Removing:** click-deselect (835), Undo (1619), Undo stroke (1587), and the
  unpaint brush, which removes every selected segment within 28 px (1410-1436).
  - **Sequencer (1731-1832):** builds adjacency where stored endpoints are less
  than 0.0001° apart, walks each connected group, then groups by `route_name`
  (1835).

  ## Bug 1: the snap jumps to the cross street at intersections
  1. **The pick is still made under the cursor (1319).** Score is distance times
  penalty, so at the shared node the distance is about 0 for every edge there
  and the direction penalty stops mattering. Ties go to whichever feature
  `queryRenderedFeatures` returns first (strict `<` at 1323).
  2. **The lookahead can only accept or reject that one pick (1386-1391).** It
  never re-picks the road the stroke actually followed. A wrong pick is either
  committed, because |dot| ≥ 0.38 accepts anything within about 68°, or dropped,
  which leaves a gap.
  3. **The continuity bonus doesn't separate the two roads (1310-1317).** The
  continuing street and the cross street share the intersection vertex, so both
  get the 0.58 multiplier. `lastCommittedEdge` is also about 8 snaps (roughly
  400 ms) behind the cursor, and it is stored in screen pixels and never reset
  at pointer down (969-977). After the map is panned or zoomed between strokes,
  it boosts arbitrary edges.
  4. **Behaviour depends on device and zoom.** Momentum is counted in pointer
  events, so 60 Hz and 1000 Hz mice behave differently. All the thresholds are
  fixed pixel values that don't scale with zoom.
  5. **Small timing offset:** `strokeIdx` is recorded 50 ms after the point was
  captured (987 vs 1445).
